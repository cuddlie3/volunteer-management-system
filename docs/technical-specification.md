# Техническое задание

## 1. Назначение и область применения

### 1.1. Назначение системы

Volunteer Management System — веб-приложение для управления волонтёрами спортивных и массовых мероприятий.

Система предназначена для централизованного хранения информации о волонтёрах, распределения их по рабочим зонам и сменам, контроля присутствия и автоматического расчёта отработанных часов.

### 1.2. Область применения

Система применяется организаторами спортивных и массовых мероприятий, в которых участвует большое количество волонтёров.

Основная задача системы — заменить разрозненное использование Google Sheets, мессенджеров и отдельных списков единой системой управления.

---

## 2. Роли пользователей и права доступа

### 2.1. Координатор

Координатор имеет полный доступ к основным функциям системы.

Права:

* добавление и редактирование волонтёров;
* просмотр списка волонтёров;
* создание и редактирование рабочих зон;
* создание и редактирование смен;
* распределение волонтёров;
* назначение задач;
* просмотр присутствия;
* редактирование информации о присутствии;
* просмотр отработанных часов;
* формирование итоговых отчётов.

### 2.2. Ответственный за зону

Ответственный работает только с назначенной ему рабочей зоной.

Права:

* просмотр назначенных волонтёров;
* просмотр расписания своей зоны;
* фиксация присутствия;
* просмотр назначенных задач;
* просмотр информации о текущей смене.

### 2.3. Волонтёр

Волонтёр имеет ограниченный доступ к собственной информации.

Права:

* просмотр личного профиля;
* просмотр назначенной смены;
* просмотр рабочей зоны;
* просмотр назначенной задачи;
* просмотр информации о времени работы.

---

## 3. Функциональные модули

### 3.1. Модуль авторизации

Предназначен для входа пользователей в систему и определения их роли.

Основные функции:

* вход в систему;
* выход из системы;
* проверка прав доступа;
* разграничение доступа в зависимости от роли.

### 3.2. Модуль управления волонтёрами

Предназначен для хранения и управления информацией о волонтёрах.

Основные функции:

* добавление волонтёра;
* редактирование данных;
* просмотр профиля;
* поиск волонтёра;
* просмотр общего списка.

### 3.3. Модуль рабочих зон

Предназначен для создания и управления зонами мероприятия.

Примеры зон:

* старт;
* финиш;
* информационная палатка;
* пункт питания;
* регистрация;
* зона выдачи стартовых пакетов.

### 3.4. Модуль смен

Предназначен для создания и управления рабочими сменами.

Смена содержит:

* дату;
* время начала;
* время окончания;
* рабочую зону;
* назначенных волонтёров;
* ответственного.

### 3.5. Модуль распределения

Предназначен для назначения волонтёров на конкретные зоны и смены.

Координатор выбирает волонтёра, рабочую зону, смену и задачу.

### 3.6. Модуль контроля присутствия

Предназначен для фиксации фактического присутствия волонтёров.

Возможные статусы:

* присутствует;
* отсутствует;
* заменён.

### 3.7. Модуль учёта часов

Предназначен для хранения времени начала и окончания работы и автоматического расчёта продолжительности смены.

### 3.8. Модуль отчётов

Предназначен для формирования итоговой информации по работе волонтёров.

Основной отчёт содержит:

* имя волонтёра;
* количество смен;
* отработанные часы;
* информацию о присутствии.

---

## 4. Сущности данных и связи между ними

### 4.1. User

Хранит данные учётной записи пользователя.

Основные поля:

* `id`;
* `login`;
* `password_hash`;
* `role`.

### 4.2. Volunteer

Хранит информацию о волонтёре.

Основные поля:

* `id`;
* `full_name`;
* `phone`;
* `email`;
* `status`.

### 4.3. Zone

Хранит информацию о рабочей зоне.

Основные поля:

* `id`;
* `name`;
* `description`.

### 4.4. Shift

Хранит информацию о рабочей смене.

Основные поля:

* `id`;
* `date`;
* `start_time`;
* `end_time`;
* `zone_id`.

### 4.5. Assignment

Связывает волонтёра со сменой и рабочей зоной.

Основные поля:

* `id`;
* `volunteer_id`;
* `shift_id`;
* `task`;
* `status`.

### 4.6. Attendance

Хранит информацию о фактическом присутствии волонтёра.

Основные поля:

* `id`;
* `assignment_id`;
* `check_in`;
* `check_out`;
* `attendance_status`.

### 4.7. Связи между сущностями

* один пользователь имеет одну роль;
* один волонтёр может участвовать в нескольких сменах;
* одна смена относится к одной рабочей зоне;
* одна рабочая зона может содержать несколько смен;
* один волонтёр может иметь несколько назначений;
* одно назначение относится к одному волонтёру и одной смене;
* для каждого назначения может храниться информация о присутствии.

---

## 5. Внешние интеграции

В первой версии системы обязательные внешние интеграции отсутствуют.

В дальнейшем возможно добавление:

* Telegram или WhatsApp для уведомлений;
* Google Sheets для импорта существующей базы волонтёров;
* электронной почты для отправки уведомлений.

Данные интеграции не входят в первую версию системы.

## 6. Технологический стек

### Frontend

**HTML, CSS, JavaScript**

Используются для создания пользовательского интерфейса веб-приложения.

Выбор обусловлен тем, что эти технологии подходят для разработки простой веб-системы и не требуют установки отдельного приложения на устройство пользователя.

### Backend

**Python + FastAPI**

FastAPI используется для реализации серверной части приложения и REST API.

Выбор Python обусловлен простотой разработки и возможностью дальнейшего расширения проекта.

FastAPI позволяет создавать API с небольшой сложностью и подходит для учебного проекта.

### База данных

**PostgreSQL**

Используется для хранения пользователей, волонтёров, зон, смен, назначений и данных о присутствии.

PostgreSQL выбран как реляционная база данных, поскольку между основными сущностями системы существуют чёткие связи.

### ORM

**SQLAlchemy**

Используется для взаимодействия серверной части приложения с базой данных.

### Контроль версий

**Git + GitHub**

Git используется для контроля версий исходного кода, а GitHub — для хранения и совместной работы с репозиторием проекта.

## 7. Ограничения и допущения

### Ограничения

* первая версия является веб-приложением;
* система не предусматривает отдельное мобильное приложение;
* первая версия не содержит интеграции с WhatsApp и Telegram;
* система рассчитана на использование в рамках одного мероприятия;
* для работы необходим доступ к интернету;
* доступ к системе осуществляется через авторизацию.

### Допущения

* пользователи имеют доступ к современному веб-браузеру;
* координаторы самостоятельно добавляют и корректируют информацию о волонтёрах;
* данные о времени начала и окончания работы вводятся ответственным пользователем;
* один волонтёр может участвовать в нескольких сменах;
* структура рабочих зон и задач может изменяться в зависимости от мероприятия.

---

## 8. Ожидаемый результат

В результате разработки должна быть создана веб-система, которая позволяет координаторам централизованно управлять волонтёрами, распределять их по рабочим зонам и сменам, фиксировать присутствие и автоматически рассчитывать отработанные часы.

Система должна сократить количество ручных операций и уменьшить риск потери или дублирования информации при организации работы волонтёров.
